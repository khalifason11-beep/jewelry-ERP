Every decision taken under ambiguity, or confirmed by the client, is recorded here with its
context, the options considered, the choice, and how to change it later. Newest entries are at
the bottom of each section. `CLIENT-PENDING` marks a default that still needs the client's final
word.

## 5. Phase 2a decisions (integrity foundation)

| # | Context | Options | Choice | How to change later |
|---|---|---|---|---|
| D-2a-0 | Re-auth window (client request) | constant vs setting | **Setting `security.reauthWindowMinutes`**, default **5**, allowed **1–30**, validated, audited and versioned like every setting (Settings → Security → "Password re-confirmation valid for"). `POST /auth/reauth` reports the current value. | Settings screen. |
| D-2a-1 | Status columns | PostgreSQL `ENUM` types vs `TEXT` + `CHECK (col IN …)` | **`TEXT` + `CHECK`**. A CHECK can be added `NOT VALID` and validated without rewriting the table; a value can later be added or retired with a plain forward migration (an ENUM value can never be removed). The single list of rules is `shared/src/db-checks.ts`, built from the enums in `shared/src/enums.ts`; a test compares the live database with it, so an enum value added without a migration fails the build. `audit_logs.action` is deliberately **not** constrained (the list grows every phase; an unknown action must never block writing an audit entry). | New migration updating the constraint + the enum. |
| D-2a-2 | Validating constraints on existing data | validate and fail the deploy on bad rows vs delete/fix rows vs keep unvalidated | Every constraint is added **`NOT VALID`** (enforced at once for new and changed rows) and then **validated** one by one. A constraint whose existing rows violate it is **left `NOT VALID` with a warning**: the deploy goes on, nothing is deleted or rewritten, and the **server logs the list at every start-up**. Verified on a copy of the demo DB (all 75 validated) and on a deliberately broken copy (one left NOT VALID, new bad rows still refused). | Correct the rows, then `ALTER TABLE … VALIDATE CONSTRAINT …`. |
| D-2a-3 | Constraint set | — | Karat **1–24** everywhere; weights **≥ 0** and **net ≤ gross**; money **≥ 0**, expenses **> 0**; and cross-field sums that the demo data already satisfied: `total_cost = purchase + making + other`, `sales.total = subtotal − discount_total`, `sale_items.final_price = list_price − discount`, movement direction ±1, transfer source ≠ destination. `hasad_redemptions.difference_mg` stays signed (it is a difference). Item **history** accepts the two purchase lifecycle steps `PURCHASED` and `RECEIVED` besides the item statuses. | `shared/src/db-checks.ts` + migration. |
| D-2a-4 | Append-only ledgers | trigger only vs privileges only vs both | **Both, independently.** `audit_logs`, `inventory_movements`, `item_status_history`, `gold_rates` (and `settings_history` from 1b) refuse `UPDATE`, `DELETE` and `TRUNCATE` by **trigger**, and on real PostgreSQL the **application role loses those privileges** (`REVOKE` in migration 0004; a superuser such as embedded PGlite is exempt from privileges, not from the triggers). Tests prove each layer separately, including a role that grants itself the privileges back. Corrections are always new rows. The demo reset drops and recreates the schema, which neither layer blocks (demo only). | — |
| D-2a-5 | Idempotency | optional vs required key; what to store | Routes flagged `idempotent` in the matrix (**create sale, void sale, create purchase, create expense, review expense, create transfer, receive transfer, complete Hasad withdrawal**) **require** an `Idempotency-Key` header (**428** without it). Keys are **per user**. Same key + same method/path/body (canonical JSON) → the **stored response is replayed** (`Idempotent-Replayed: true`); same key + different request → **422**; same key while the first is still running → **409 IN_PROGRESS**. Only **2xx** results are stored (already cost-filtered for that user), written **before** the response is sent; a non-2xx result releases the key (nothing was created, e.g. `REAUTH_REQUIRED` then retry). A reservation older than **5 min** without a result answers **409 IDEMPOTENCY_UNCERTAIN** (never re-run: the record may exist). Keys are kept **24 h**. The frontend keeps **one key per action** (a cart, a form, "receive transfer X"), reuses it for double clicks, network retries and the retry after re-auth, joins concurrent submits of the same key client-side, and replaces it only after success. | `backend/src/core/idempotency.ts`, `frontend/src/lib/idempotency.ts`; retention/stale constants there. |
| D-2a-6 | Money and weight arithmetic (L-7) | float + `Math.round` vs integer | **Exact integer arithmetic** in `shared/src/money.ts`: BigInt intermediates, rounding **half away from zero** (symmetric for negatives; `Math.round(−2.5) = −2` is not), unsafe inputs throw instead of guessing. Settlement amount = `round(|Δmg| × rate / 1000)`; pure-gold = `round(mg × karat / 24)`; the Hasad blended rate is a weighted average in integers; typed grams are parsed as decimal strings. The old float formula was provably wrong in real cases (9 mg at 190 500/g = 1 714.5 → it gave 1 714 instead of 1 715). Property tests (fast-check, 2 000 cases each) cover rounding, symmetry, round-trips and the settlement rule. | — |
| D-2a-7 | Cost visibility guarantee (replaces the D-1b-16 name list) | name list vs schema-driven registry | **One registry, `shared/src/field-classification.ts`**, classifies **every database column** (test walks the Drizzle schemas, ERP and Hasad mock) and **every API response field** as COST or SAFE. The response filter is driven by it. Tests fail the build when a column is unclassified or stale, when a COST column could surface under a SAFE name, when **any response in any test** (POST replies included, checked after every test file) carries an unclassified field name, or when a COST field reaches a branch manager or cashier on **any GET route** (all routes, all report variants, nested objects and arrays, report column descriptors). Free-form containers (audit params and metadata, settings values, external payloads) are searched for COST names but their inner keys are not required to be registered; data keys (karats, codes, setting keys) are recognised by pattern. **Found and fixed while building it:** audit entries showed branch managers the purchase cost inside the description text ("… cost 45,000,000"). Audit entries are now redacted at read time: COST-named parameters become `{ hidden: true }` (shown as "—") and the English text is re-rendered; the stored rows are untouched. | Add new fields to the registry; the tests say which. |
| D-2a-8 | Races (M-3, M-4 and more). **Hasad gap RESOLVED by scope change (REM-2, D-rem2-1): the Hasad integration no longer exists, so there is no double notification.** | — | Row locks (`SELECT … FOR UPDATE`) plus a status condition on the update: **expense review** (M-3), **transfer receive** (M-4), **Hasad open** (a concurrent second open joins the first draft) and **Hasad complete** (the withdrawal and draft are locked and re-checked). Item locks are always taken **in id order**, so overlapping carts cannot deadlock. | D-2a-9 | Test infrastructure | PGlite only vs real PostgreSQL | Two vitest projects: **pglite** (fast, no install) and **postgres**, which re-runs **every suite** on real PostgreSQL plus `test/pg/**` (races, privileges). | D-2a-10 | Lockout under a burst of parallel attempts | count after verifying vs reserve before | **Reserve, then verify.** Each sign-in (and each re-auth / change-password check) first reserves a failure with one atomic `UPDATE … WHERE not locked`; the reservation that reaches `lockoutThreshold` **sets the lock in the same statement**, so every concurrent attempt after it is refused without verifying.
